# v0.3.0 — avatar animation fast path

The milestone that makes a continuously changing avatar the renderer's
first-class workload, and so `hydra-toon`'s most important one: a renderer
for continuously moving avatars rather than a general Hydra renderer
([design policy §2](../design/DESIGN_POLICY.md#2-core-concept), §11–§14).

**Done when**, a representative VRM avatar's ordinary pose, morph, expression,
look-at and camera changes use the existing renderer fast path through a
`usd-avatar-runtime` evaluated-state adapter, without scene or pipeline rebuilds
or full geometry uploads. Reports must establish Hydra/direct parity and
producer-to-submit/present-API-return timing on the dedicated Vulkan viewport.

This milestone closes the renderer's integration boundary and evidence. It
does not require the whole avatar runtime, full MMD evaluation, OpenExec,
WebGPU, multi-avatar scheduling or a stable renderer C ABI. The runtime's
contracts and implementation are owned by its
[roadmap](https://github.com/animu-sphere/usd-avatar-runtime/blob/main/docs/roadmap/current.md).

## Evaluated-state adapter and representative-avatar evidence

The optional adapter accepts separate canonical base RGB and scalar alpha via
explicit `BaseColorRgb`/`Alpha` bindings, with independent override release and
overlap rejection. The runtime's
[scoped motion-check host](https://github.com/animu-sphere/usd-avatar-runtime/blob/main/docs/architecture/OUTPUT_PATHS.md#scoped-toon-transport-check)
now exercises installed consumer transport with real-owner values and generated
probe resources. The Hydra delegate now describes an actual avatar's resident
mesh/material paths, palette joint identities, inverse binds, placement and
subshape slots
([renderer report 43](../reports/renderer/43-2026-10-10-hydra-resident-targets.md)).
Binding runtime results to them and rendered parity remain the acceptance
work below.

Validate the consumer contract with real `usd-avatar-runtime` providers and
extend the optional adapter's material mappings for their canonical outputs.
Prepare runtime-to-resident bindings in the external host by matching the
runtime's target identities to the described resident identities, listing
each shape's described subshape slots so the adapter interpolates its
inbetweens; keep runtime and format types out of core/backend headers
([integration scope §4](../design/INTEGRATION_SCOPE_POLICY.md#4-dependency-rules),
[placement rules](../architecture/PROJECT_LAYOUT.md#3-where-new-code-goes)).

Use a minimal external host that consumes completed results from the runtime's
composition of motion/format evaluator providers. Renderer code consumes those
results without invoking evaluators. The static asset may be prepared through
Hydra; a general Hydra-free asset loader is not required here.

Verify in the dedicated viewport:

- bone-based and expression-based gaze, using representative avatars or
  controlled fixtures covering both routes;
- combined expression, viseme, blink and gaze input, with arbitration performed
  once by the source owner's evaluator;
- mapped inbetween subshape weights and canonical material-value changes;
- a newly published result arriving after ordinary scene evaluation and draw
  extraction, applied with only the affected joint/weight/material writes;
- real-provider frame/binding identity and lifetime through replacement/reset,
  with source-owner diagnostics for unsupported output types.

## Hydra and direct-path parity

Send each completed runtime result to both output paths, without a second
evaluation or per-frame USD authoring. Compare the resulting target mapping,
transforms/joint palettes, subshape weights, normalized materials, draw packet
membership and pipeline selection, then colour/depth on the same Vulkan
configuration with declared tolerances
([design policy §34](../design/DESIGN_POLICY.md#34-evaluated-avatar-input-and-transport-parity)).
Exercise value-only updates and structural rebinding; image equivalence must
not hide missing effects or unexpected scene sync and static uploads.

## Producer-to-submit and present-return latency evidence

Use producer timestamps, explicitly mapped to the host's monotonic clock,
to report source-produced motion, expression and gaze sample ages through
runtime publication, late read, buffer write, submit and present API return
([design policy §23–§24](../design/DESIGN_POLICY.md#23-performance-kpis)).
Retain the input's original timestamp when a previous valid result remains
displayed. Evaluation/publication time and USD time selection are not
sensor-production timestamps; present API return is not scanout. Label
generated-source timing as such, and leave missing source timestamps unmeasured.
Published runtime state carries no source time, only the host's input
revision, so the host keeps each selected input's times by that revision and
supplies them with the scene the adapter reads. A connector pose from a
source without its own clock is stamped with its receive time
([`motion-connectors` connector contract §6](https://github.com/animu-sphere/motion-connectors/blob/main/docs/design/CONNECTOR_CONTRACT.md#6-time));
report it from receipt, not as a producer age. An input the host reports
unavailable has no sample to age and is left unmeasured.

Actual display instrumentation and motion-to-photon evidence are deferred to
[not yet in a milestone](README.md#not-yet-in-a-milestone). They are not a
v0.3.0 release gate, and this milestone must make no measured-display claim.

## Viewport animation and latency diagnostics

The dedicated viewport
([design policy §31](../design/DESIGN_POLICY.md#31-evaluation-hosts)) grows
what this milestone is judged with:

- source-owner mapping diagnostics associated with the runtime frame and
  bound renderer targets;
- source expression names and canonical material-input mappings associated
  with the published runtime result and resident renderer slots.

## Fast and slow state kept apart

Extend the fast/slow separation evidence to runtime-produced ordinary avatar
expressions and gaze. A value-only fast change never dirties slow state
([design policy §14](../design/DESIGN_POLICY.md#14-dirty-propagation)); the
telemetry is how this milestone shows it. Record sync counts, structural
revisions, static uploads and affected dynamic writes during ordinary motion,
plus the explicit structural fallback/rebinding case. Also verify that core,
backend and Hydra-only builds remain independent of the optional runtime
consumer contract.
