## TL;DR

**Report 02's ask and question are both answered. After porting template
0.5.3's install smoke, `ost test` on `core` turns `renderer.install_tree` into
PASS. `ost lock` restores the `core` pin after a `lookdev` build.**

1. **Resolved in the template:** the install-tree CTest merges its verdict
   into `renderer-report.json` (02 §3). The fix is in
   `validation/run-install-smoke.cmake.in`, which had to be ported by hand
   (§2.1).
2. **Answered:** `strata.lock` records the project's configuration, and
   `ost lock` restores the default pin after a build with another profile
   (02 §4; §2.2).
3. **Observation, new:** every `ost build` rewrites `strata.lock` with LF
   line endings. With `core.autocrlf=true`, the file then shows as modified
   although `git diff` is empty (§3).

### 2.1 `renderer.install_tree` on `core`

As the release notes say, `ost` does not re-apply a template. A scaffold
generated with 0.23.8 differs from this repository in eight files. Only
`validation/run-install-smoke.cmake.in` differs in behaviour. The others
differ in comments, in the `hd/version.h` include order, in this
repository's own edits (README, `.gitignore`, the `hydra` intent), in
`openstrata.scaffold.yaml`, or in the platform a fresh `ost init` now
defaults to (`cy2027`). After the
headless smoke, the new script reads the installed
`renderer-install-report.json`. If that report does not contain a
`renderer.install_tree` check, or the check did not pass, the script fails.
Otherwise it replaces the check of the same id in the build tree's
`renderer-report.json`. `validation/CMakeLists.txt` already set
`RUN_SERIAL` on the test, as the template's comment requires.

```text
$ ost build && ost validate
  [skip] renderer.install_tree — run the renderer install-tree CTest (producer ost-build-aca639601313eb2d)
Result: passed

$ ost test
3/3 Test #3: toon-renderer-install-tree .......   Passed    0.33 sec

$ ost validate
  [ok  ] renderer.install_tree — producer ost-test-b27e0b97a284d6c0
Result: passed
```

The PASS survives a no-op `ost build`. A rebuild that produces a new report
returns the check to SKIP until the next `ost test`. The detail now describes
the missing step correctly.

The `hydra` intent built, ran 7 of 7 tests and passed `ost validate` with
all thirteen renderer assertions PASS. `ost renderer viewport -- --frames 8
--hidden` presented 8 frames, and `ost validate --intent renderer-viewport`
passed.

### 2.2 `strata.lock`

A `lookdev` build still rewrites `strata.lock` to the `lookdev` runtime. The
release notes define the file as a configuration record and say to run
`ost lock` after using another profile. `ost lock` wrote the `core` pin
back, with `"validation": "pending"` as committed, and `ost lock --check`
reported it up to date.

## 3. Observation — `ost build` rewrites `strata.lock` with LF endings

This checkout has `core.autocrlf=true`, so `strata.lock` is checked out
with CRLF endings. Every `ost build`, including one with nothing to do,
writes the file back with LF. So does `ost lock`. `git status` then lists
the file as modified, and `git diff` shows nothing. `ost test` and
`ost validate` leave the file alone. It was not checked whether 0.23.7
did the same.

**Ask (P3):** write `strata.lock` only when its content changes, or keep
the line endings already on disk.
