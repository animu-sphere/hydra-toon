## TL;DR

**All five of report 04's asks are answered. The Formation of the canonical
`lookdev` runtime, `vrmImaging` and `toon` resolves, locks and passes
`doctor`, and `ost formation run` renders the VRM session with every VRM
material selecting MToon. Two things stood in the way of `run`, and neither is
ours.**

1. **Q1, blocking the declared command:** `formation run` gives its command a
   `PATH` of the Formation's directories only, and the `lookdev` runtime ships
   no Python (`python.provider = platform`), so `usdview` and `testusdview`
   cannot start. `doctor` reports the same command reachable (§3;
   [open-strata#259](https://github.com/animu-sphere/open-strata/issues/259)).
2. **Q2:** the materialization root sits under the manifest's directory, about
   100 characters deep. From a 104-character directory, the runtime's Qt
   platform plugin is 254 characters long, and Qt cannot load it (§4;
   [open-strata#260](https://github.com/animu-sphere/open-strata/issues/260)).
3. **Observation:** a Formation that lists `vrmSchema` beside a `vrmImaging`
   that carries it resolves with no conflict; OpenUSD registers one copy and
   drops the other without a word (§5).
4. **Observation:** the renderer component puts its `lib` on `PATH` twice (§5).

## 3. Q1 — `formation run` cannot start the runtime's viewer

The Formation's command was `testusdview`, from the runtime's `bin`:

```text
$ ost formation doctor formation.toml
  [✓] formation.command — 'testusdview' is reachable in the composed environment
$ ost formation run formation.toml
error[FORMATION_LAUNCH_FAILED]: cannot launch 'testusdview': program not found
```

`testusdview` is an extensionless Python script, and `run` does not launch it
the way `doctor` finds it. Its `.cmd` shim, `testusdview.cmd`, does launch,
and runs `python "%~dp0testusdview"`, which fails with `'python' is not
recognized`: inside `run`, `PATH` holds the Formation's eight directories and
nothing else, and the runtime has no interpreter. Its manifest says
`openusd_compatibility.python.provider = platform`, version 3.13.14; `ost
runtime validate` rendered through the host's
`C:\Users\…\Python313\python.exe`. The platform interpreter the runtime was
validated with is not part of the Formation. The rest of the parent
environment passes through; only `PATH` is replaced.

The session ran by overriding the command with the host interpreter's
absolute path and a four-line launcher that finds `testusdview` on the
composed `PATH`:

```sh
ost formation run formation.toml -- C:/…/Python313/python.exe run_testusdview.py \
    <stage> --renderer Toon --testScript vrm_material_check.py
```

That puts a machine path into every invocation, and the Formation's own
`[command]` cannot be run. On Linux the script's `#!/usr/bin/env python3`
would meet the same `PATH`; that was not run.

**Ask (Q1):** make the platform interpreter the runtime declares, and was
validated with, part of the Formation environment — on `PATH`, or recorded in
the lock and used to launch the runtime's Python entry points — so that
`[command] program = "usdview"` runs. Make `doctor`'s reachability check apply
the rules `run` launches by. Raised as
[open-strata#259](https://github.com/animu-sphere/open-strata/issues/259).

## 4. Q2 — the materialization root is deep enough to break Qt

`run` and `env` materialize under
`<manifest dir>/.strata/formations/<name>/materialized/<pid>-<nanoseconds>/`,
and the runtime's PySide6 puts its platform plugins another
`runtime/lib/python/PySide6/plugins/platforms/` below that. With the manifest
in a 104-character directory, `qwindows.dll` was 254 characters long. Qt found
it and could not load it:

```text
qt.core.library: "…/materialized/34892-1790437411141138000/runtime/lib/python/PySide6/plugins/platforms/qoffscreen.dll"
  cannot load: Cannot load library …: The filename or extension is too long.
qt.qpa.plugin: Could not load the Qt platform plugin "offscreen" in "" even though it was found.
```

The process exits with `0xC0000409`, and on the desktop Qt raises a modal
"no Qt platform plugin could be initialized" dialog that holds the run until
it is dismissed. `LongPathsEnabled` is 1 on this machine; it does not help a
loader that is not long-path aware. Moved to `C:\dev\hydra-toon\formations\vrm-usdview`
(179 characters to `qwindows.dll`), the same Formation ran.

**Ask (Q2):** a materialization root that does not grow with the manifest's
directory — under the `ost` store, keyed by a short digest — or a `doctor`
check that reports the deepest materialized path against `MAX_PATH` on
Windows. Raised as [open-strata#260](https://github.com/animu-sphere/open-strata/issues/260).

## 5. Observations

- **A plugin listed twice.** With `vrmSchema` 0.9.0 (`sha256:beaf8468…`) as a
  component beside `vrmImaging`, whose package carries the same `vrmSchema`
  under `runtime/bundles/`, `resolve` reports `conflicts: none`, and `lock` and
  `doctor` pass. `PXR_PLUGINPATH_NAME` names two `vrmSchema` directories, and
  inside `run` OpenUSD's `Plug.Registry` holds one `vrmSchema`, the
  standalone component's, with no warning. Here both are the same build. Had
  they differed, `vrmImaging` would load against a `vrmSchema` it was not
  built with. The Formation guide says duplicate plugin identities are
  rejected; a bundle inside a component is not compared with a component.
- **`lib` twice on `PATH`.** The lock records two `PATH` entries for `toon`,
  `[lib]` and `[bin, lib]`; the package manifest declares `bin` and `lib`
  once each. Harmless.
- **Run evidence has empty `stdout` and `stderr`** for a command that printed
  to both. The command's streams go to the console, so the fields are never
  filled; the run record is otherwise complete (digests, lock, exit code).
