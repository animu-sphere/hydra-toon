# The renderer template bootstraps, and needs two fixes on OpenUSD 26.08 and a Japanese host

> Superseded by [report 02](02-2026-09-26-v0.23.7-report-01-reverified.md): `ost` 0.23.7 resolves every ask here, and §2's `core` install-tree PASS is corrected there.

- Date: 2026-09-26
- Version exercised: `ost 0.23.6`, renderer template 0.5.1, on this
  workstation (Windows 11, MSVC 14.51, NVIDIA RTX A5000), runtimes
  `cy2026-windows-x86_64-py313-core` and `…-lookdev` (OpenUSD 26.08)
- Occasion: creating `hydra-toon` from the template
  ([PROJECT_LAYOUT.md §1](../../architecture/PROJECT_LAYOUT.md#1-what-the-project-is))
- Prior report: none here. The ecosystem's series is `usd-vrm-plugins'`
  ([reports](https://github.com/animu-sphere/usd-vrm-plugins/tree/main/docs/reports/ost)),
  and the renderer precedent is `hydra-merlin`'s
  [report 01](https://github.com/animu-sphere/hydra-merlin/blob/main/docs/reports/ost/01-2026-07-11-renderer-template-foundation.md)
- Next ask target: `ost 0.23.7`

## TL;DR

**The template does what it says on a clean repository: headless GPU
evidence, `testusdview` host evidence and the viewport all pass after two
local fixes. Two `ost` behaviours turn a passing `ost validate` into a
failure without anything having changed.**

1. **Worked:** `ost init`, `ost build`, `ost test` and `ost validate` on the
   `core` profile, first time, with every GPU check PASS on real hardware (§2).
2. **P1: a no-op `ost build` invalidates the renderer evidence.** Build,
   validate — passed; build again with nothing to do, validate — FAILED
   (§4.1).
3. **P1: the Hydra adapter does not compile against OpenUSD 26.08.**
   `HdRendererCreateArgs` is a container schema from `HD_API_VERSION` 98, and
   the template still reads `args.gpuEnabled` (§3.1).
4. **P2: `ost renderer viewport` leaves `ost validate` FAILED** for the
   default target, and the intent it builds cannot itself be validated (§4.2).
5. **P3: C4819 on a CP932 host.** The template's sources contain UTF-8 and
   its MSVC flags do not include `/utf-8` (§3.2).
6. **P3: `frame.contexts: 3`** in the generated manifest does not describe the
   generated backend, which runs one frame in flight (§5).

## 1. What was done

```sh
ost init --template renderer --name toon --platform cy2026
ost build --check
ost build --jobs auto
ost test
ost validate
ost build --profile lookdev --intent hydra --jobs auto   # after declaring the intent
ost test --profile lookdev --intent hydra
ost validate --profile lookdev --intent hydra
ost renderer viewport -- --frames 8 --hidden
```

The `hydra` intent is project-declared in `openstrata.toml`
(`TOON_ENABLE_HYDRA2=ON`), following `hydra-merlin`'s `viewport-usd`.

## 2. Worked

- `ost init` wrote 38 files plus `openstrata.toml` and `openstrata.scaffold.yaml`;
  `--name toon` produced `Toon`, `hdToon`, `include/toon/` and `TOON_`
  consistently.
- The `core` build configured and built in about 6 s. `renderer-report.json`
  recorded every GPU check PASS: 1,000 deterministic frames, colour and depth
  read back, no validation messages, device `NVIDIA RTX A5000` (API 1.3.280),
  loader 1.4.350. The Hydra checks were explained `SKIP`s naming the option to
  set.
- `ost test`: 3 of 3. `ost validate`: passed, with `renderer.install_tree`
  taking its PASS from the test producer.
- The `hydra` intent, after §3.1's fix: `ost test` 7 of 7 in 6.3 s, including
  `toon-renderer-usdview-host` (5.5 s), and `ost validate` passed with all
  thirteen renderer assertions PASS. `usdview-first-frame.png` shows the
  triangle.
- `ost renderer viewport -- --frames 8 --hidden` fetched GLFW 3.4, built,
  and presented 8 frames with no swapchain recreation.

## 3. Template defects

### 3.1 P1 — `HdRendererCreateArgs::gpuEnabled` on OpenUSD 26.08

```text
adapters\hydra2\src\renderer_plugin.cpp(19): error C2039: 'gpuEnabled':
'pxrInternal_v0_26_8__pxrReserved__::HdRendererCreateArgsSchema' のメンバーではありません
```

The template's `IsSupported` reads `args.gpuEnabled`. In 26.08
(`HD_API_VERSION` 98) the argument is a container schema. Fixed here as
`hydra-merlin` fixed it: under `#if HD_API_VERSION >= 98`, read
`args.GetGpuEnabled()` and treat an absent source as enabled.

**Ask:** carry that branch in the template. Its own test suite would have
caught this against any 26.08 runtime.

### 3.2 P3 — C4819 on a CP932 host

```text
adapters\headless\main.cpp(1): warning C4819: ファイルは、現在のコード ページ (932)
で表示できない文字を含んでいます。
```

The cause is one em dash in a comment (line 270). Harmless here, but on this
host every such character is a warning, and under `/WX` it would be an
error. Fixed here by adding `/utf-8` to the MSVC options; a forced rebuild of
`main.cpp` was then clean.

**Ask:** add `/utf-8` to the template's MSVC flags, or keep template sources
ASCII.

## 4. Validation that fails without a change

### 4.1 P1 — a no-op `ost build` unbinds the renderer report

Reproduced twice on the `core` target:

```text
touch adapters/headless/main.cpp && ost build   # relinks toon-headless, rewrites the report
ost validate                                    # Result: passed
ost build                                       # nothing to do
ost validate
  [FAIL] renderer-evidence — …\renderer-report.json is invalid: managed producer
         'ost-build-168443480f50e482' does not bind renderer report
         'renderer-report.json' in its completion evidence
Result: FAILED
```

The no-op build leaves `renderer-report.json` untouched, so the report still
names the build that wrote it. That is the intended rule: "an untouched report
keeps its earlier owner"
([adopting a renderer project §3](https://github.com/animu-sphere/open-strata/blob/main/docs/guides/adopt-a-renderer-project.md#3-validate-and-record-evidence-bound-to-a-producer)).
But the no-op build rewrites `.ost-build-complete.json` with its own
invocation and no `renderer_reports` entry. The earlier owner's binding is
lost with it, so the report can no longer be verified. `ost test` does not
repair it, because it binds only `renderer-ctest-report.json`. Anything that
changes the headless runner's inputs repairs it.

**Ask:** a completion record that binds no report carries forward the
bindings of the reports it did not touch. Or `renderer-evidence` accepts a
report whose producer's completion has been superseded by a no-op build of
the same fingerprint.

### 4.2 P2 — the viewport launch record fails the default target

After `ost renderer viewport`, which builds its own tree
(`build/<target>--renderer-viewport`):

```text
$ ost validate
  [FAIL] renderer-viewport — viewport launch describes a different build directory
Result: FAILED

$ ost validate --intent renderer-viewport
error[INVALID_CONFIG]: unknown build intent 'renderer-viewport'

$ ost validate --build-dir build/cy2026-windows-x86_64-py313-core--renderer-viewport
  [FAIL] renderer-evidence — … managed producer 'ost-build-…' does not bind renderer
         report 'renderer-report.json' in its completion evidence
```

The launch record is `.strata/renderer-viewport/<target>/launch.json`. It
names its own build directory and `intent.name = renderer-viewport`. With it
moved aside, `ost validate` passed again. So a repository that runs the
README's viewport command cannot pass validation, and there is no command
that validates the viewport build it made.

**Ask:** key the durable viewport record to the intent's build, and have the
default target's `renderer-viewport` check `SKIP` a record from another
build, or accept the built-in intent in `ost validate --intent`.

## 5. P3 — `frame.contexts: 3`

The generated `openstrata.renderer.yaml` declares `frame.contexts: 3`, and
the manifest validator requires only ≥ 1. The generated swapchain path runs
one frame in flight, as its header comment says. `hydra-toon`'s policy is
one ([design policy §18](../../design/DESIGN_POLICY.md#18-frames-in-flight)),
so the manifest now says 1.

**Ask:** state what `contexts` asserts, and generate the value the generated
backend uses.

## 6. Observations, not asks

- **Mixed Vulkan SDKs worked.** `VULKAN_SDK` points at 1.3.290, which predates
  the bundled `slangc`, so headers and loader came from 1.3.290 and `slangc`
  from 1.4.350 on `PATH`. The build did not say which `slangc` it chose;
  `ost doctor` could.
- **`.strata/targets/<target>/build.log` accumulates across runs.** After the
  §3.1 fix, the successful rebuild's log still held the earlier `FAILED`
  line, which is easy to misread as the current result.
- **The Hydra path renders at a fixed 64×64** and usdview upscales it. That is
  the template's stated bootstrap scope, recorded here so the screenshot is
  not taken for a resolution bug.
