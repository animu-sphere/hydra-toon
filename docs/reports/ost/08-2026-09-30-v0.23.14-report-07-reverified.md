# `ost` 0.23.14 resolves report 07: `ost renderer viewport --intent hydra --with vrmImaging` draws the avatar in MToon, in a tree of its own

- Date: 2026-09-30
- Version exercised: `ost 0.23.14`, on the workstation of
  [report 07](07-2026-09-28-v0.23.13-a-hydra-fed-viewport.md) (Windows 11,
  MSVC 14.51, NVIDIA RTX A5000); the canonical CY2026 `lookdev` runtime
  (OpenUSD 26.08); `vrmImaging` 0.10.0 by its published digest, as the
  committed `formations/vrm-host-session/` pins it
- Occasion: re-verifying report 07's three asks against the release that
  answers them ([v0.23.14 release notes](https://github.com/animu-sphere/open-strata/blob/main/docs/releases/v0.23.14.md))
- Prior report: [07](07-2026-09-28-v0.23.13-a-hydra-fed-viewport.md)
- Next ask target: the next `ost` release

## TL;DR

**All three of report 07's asks are answered. One command now builds the
Hydra adapter and the viewport together, in a tree no other command owns,
and launches the viewport with `vrmImaging` composed from its artifact
digest: the avatar draws 20 of 20 draws MToon, as it does in the Formation.**
This repository's CMake already reads `OST_RENDERER_ADAPTERS` the way
renderer template 0.5.4 does, so nothing in the project had to change.

1. **Q1 answered:** `--intent hydra` keeps `TOON_ENABLE_HYDRA2=ON` next to
   the inserted `viewport`, and an intent that declares
   `OST_RENDERER_ADAPTERS = "hydra2;viewport"` passes preflight (§2).
2. **Q2 answered:** the run builds in
   `<target>--hydra--renderer-viewport`; the `hydra` tree's cache is
   untouched, and `ost test` and `ost validate --intent hydra` pass with
   every Hydra assertion `ok` (§3).
3. **Q3 answered:** `--with sha256:<vrmImaging>` composes the plugin and the
   `vrmSchema` it carries into the launch, and records the input (§4).
4. **Observed:** the workflow tree can be validated but not tested, so its
   Hydra assertions stay `SKIP`; redaction labels the transient plugin root
   `<project-root>`; `ost package --json` still prints CMake's install log
   first (§5).

## 1. What was done

```sh
ost --version                                        # ost 0.23.14
ost renderer viewport --intent hydra --profile lookdev \
    --with sha256:894fd616…71667 --preflight -- --usd <avatar.usdz>
ost renderer viewport --intent hydra --profile lookdev \
    --with sha256:894fd616…71667 --json --redact-paths -- \
    --usd <avatar.usdz> --hidden --frames 8 --expect-draws 20 --screenshot <file.ppm>
ost renderer viewport --intent hydra --profile lookdev -- \
    --usd <avatar.usdz> --hidden --frames 8           # without --with
ost validate --profile lookdev --intent hydra--renderer-viewport
ost test --profile lookdev --intent hydra--renderer-viewport
# a temporary intent in openstrata.toml, removed afterwards:
#   [build.intents.adapters-probe]
#   cache = { OST_RENDERER_ADAPTERS = …"hydra2;viewport" }
ost renderer viewport --intent adapters-probe --profile lookdev --preflight --json
ost build --profile lookdev --intent hydra --jobs auto
ost test --profile lookdev --intent hydra
ost validate --profile lookdev --intent hydra --strict-renderer-evidence
ost build --profile lookdev --intent viewport-usd --jobs auto
ost test --profile lookdev --intent viewport-usd
ost validate --profile lookdev --intent viewport-usd --strict-renderer-evidence
ost package --profile lookdev --intent hydra --json
```

The artifact is `usd-vrm-plugins` v0.10.0's `vrmImaging`,
`sha256:894fd616f1414d5b393ff0d50abbf7ef18cb603562133c72e642493b48f71667`,
already in this workstation's registry. The avatar is the converted
AliciaSolid of the renderer reports, which is not redistributable and is not
in the repository.

## 2. Q1 — one intent builds both adapters

The viewport workflow still inserts `OST_RENDERER_ADAPTERS=viewport` into the
`hydra` intent's cache, and the project's CMake now adds that adapter to what
the intent's options enable instead of replacing them. The tree the run
configured:

```text
OST_RENDERER_ADAPTERS:STRING=viewport
TOON_ENABLE_HYDRA2:BOOL=ON
TOON_ENABLE_VIEWPORT:BOOL=ON
```

This repository had already made that change to its own CMake with the
Hydra-fed viewport ([renderer report 19](../renderer/19-2026-09-28-hydra-fed-viewport.md));
renderer template 0.5.4's adapter block is the same code, line for line, so
applying the template's update changed nothing here.

The other half of the ask, a declared list with both adapters, is no longer
refused:

| Intent's `OST_RENDERER_ADAPTERS` | 0.23.13 preflight | 0.23.14 preflight |
| --- | --- | --- |
| `"hydra2;viewport"` | `Error[INVALID_CONFIG]` | passes, intent `adapters-probe--renderer-viewport` |

## 3. Q2 — the run has a tree of its own

| Tree | `OST_RENDERER_ADAPTERS` | Hydra | Viewport |
| --- | --- | --- | --- |
| `…-lookdev--hydra` (`ost build --intent hydra`) | empty | `ON` | `OFF` |
| `…-lookdev--hydra--renderer-viewport` (the viewport run) | `viewport` | `ON` | `ON` |

Report 07's failing sequence — a viewport run with `--intent hydra`, then an
ordinary build of `hydra` — now leaves the `hydra` tree as `ost build` left
it. After it, `ost test --intent hydra` passed 10 of 10 and
`ost validate --intent hydra --strict-renderer-evidence` passed with every
Hydra assertion `ok`. All 20 assertions carry `producer_kind: ost-test` and
`verification_class: completion-bound`, and no evidence warning was raised.

`ost validate --intent hydra--renderer-viewport` validates the workflow tree
and its launch record, as the release notes say, and passed.

## 4. Q3 — the launch composes a plugin

| Launch | `materials_mtoon` | `materials_preview` | draws MToon | outlined | transparent |
| --- | --- | --- | --- | --- | --- |
| `--with sha256:<vrmImaging>` | 12 | 1 | 20 of 20 | 15 | 5 |
| no `--with` | 0 | 13 | 0 of 20 | 0 | 0 |

These are the Formation's counts
([renderer report 13](../renderer/13-2026-09-28-host-session-formation.md)),
now from a local build of the viewport with no package and no import step.
`--expect-draws 20` passed and the frame was captured. The launch
environment adds three `PXR_PLUGINPATH_NAME` entries: the runtime's, and
`vrmSchema`'s and `vrmImaging`'s resources in a transient tree under
`%TEMP%\.ost-plugin-product-renderer-<pid>-<ns>\`, which is gone when the run
ends. The launch record carries the input digest and the resolved bundle
(`vrmImaging` 0.10.0, `usd-imaging`), and `device` is now `reported` because
`toon-viewport` prints the labels `ost` reads (report 07 §5).

## 5. Observations

- **The workflow tree cannot be tested.** `ost test --intent
  hydra--renderer-viewport` is refused, `unknown build intent`, while
  `ost validate` accepts the same name. Its Hydra assertions are therefore
  always `SKIP` ("exercised by its OpenUSD CTests"), and `validate` passes.
  That is report 07's optional Q2 item, an intent whose required adapters
  cannot validate as `SKIP`, which 0.23.14 does not take up. This repository
  keeps its `viewport-usd` intent so the viewport's Hydra CTest
  (`toon-viewport-present-usd`) has a tree it runs in: 13 of 13 passed, and
  strict validation passed.
- **Redaction calls the transient plugin root the project root.** With
  `--redact-paths`, `plugins.bundles[0].root` reads `<project-root>`; the
  unredacted record has the `%TEMP%` tree above. `<absolute-path>` or a
  transient placeholder would not mislead a reader of a public report.
- **The bundle list names `vrmImaging` only.** `vrmSchema`, which it
  carries, is on `PXR_PLUGINPATH_NAME` but not in `plugins.bundles`.
- **One launch record per workflow tree.** The run without `--with`
  replaced the record of the run with it, since both built the same tree.
  The composition is in the record, so the newest run is described
  correctly; an earlier composition is not kept.
- **`ost package --json` still prints CMake's install log** on stdout
  before the JSON document, as the release workflow's comment records for
  0.23.13; the workflow cuts the document from its first `{`.
