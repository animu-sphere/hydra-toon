### 2.3 Template fixes

`ost` does not re-apply a template, as the release notes say. The local
fixes from report 01 match template 0.5.2 line for line, with one exception:
the template also includes `<pxr/imaging/hd/version.h>`, which defines
`HD_API_VERSION`. Our copy compiled because another header pulls it in. If
that stopped, `#if HD_API_VERSION >= 98` would silently choose the pre-98
branch. The include is now explicit. The `hydra` intent then built without
warnings, ran 7 of 7 tests and passed `ost validate`.

`openstrata.scaffold.yaml` still records template 0.5.1 and `ost` 0.23.6.
That file records how the project was generated, so it is not rewritten.

## 3. P3 — `renderer.install_tree` on `core`

After `ost test` passes 3 of 3 on `core`, including
`toon-renderer-install-tree`:

```text
$ ost validate
  [ok  ] tested
  [skip] renderer.install_tree — run the renderer install-tree CTest (producer ost-build-aca639601313eb2d)
Result: passed
```

The SKIP's detail asks for the test that has just passed. The template wires
the check as follows:

- `toon-renderer-evidence` runs `toon-headless` without `--install-tree`, so
  `renderer-ctest-report.json` records the check as SKIP.
- `toon-renderer-install-tree` runs the installed `toon-headless --install-tree`
  and writes its PASS to `renderer-install/renderer-install-report.json`.
  `ost` reads no file by that name.
- Only the `hydra` intent's usdview smoke merges `renderer.install_tree` PASS
  into `renderer-report.json`.

So on `core` the check cannot pass. Report 01 §2 says the `core` validate took
`renderer.install_tree` PASS "from the test producer". That line most likely
describes the `hydra` run. It was not re-run under 0.23.6 to confirm.

**Ask:** in the template, let the `core` install-tree CTest put its verdict
where `ost validate` reads it, for example by merging it into
`renderer-ctest-report.json` as the usdview smoke merges into
`renderer-report.json`. If SKIP is intended on `core`, have the detail name
the build that can pass the check.

## 4. Observation — `strata.lock` follows the last profile built

`openstrata.toml` requires `profile = "core"`, and the committed
`strata.lock` pins the `core` runtime (`"source": "mock"`,
`"validation": "pending"`). After `ost build --profile lookdev --intent hydra`
it pins the `lookdev` runtime instead, with its digest, the `openusd` and
`materialx` extensions, `"source": "local"` and `"validation": "passed"`. A
following plain `ost build` restores the `core` content. `ost test` and
`ost validate` leave it unchanged.

So running [BUILDING.md](../../guides/BUILDING.md) top to bottom leaves a
modified lockfile in the working tree. Whether 0.23.6 did the same was not
checked. Here the lockfile is kept at the `core` pin and a `lookdev` rewrite
is not committed.

**Question:** is `strata.lock` meant to record the project's declared
profile, or the last target built? If the former, a build with a
non-default `--profile` should not rewrite it.
