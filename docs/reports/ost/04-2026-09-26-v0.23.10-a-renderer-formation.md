# A renderer Formation with a plugin does not resolve: `ost formation` refuses every packaged target, and the renderer's package cannot carry its adapter

- Date: 2026-09-26
- Version exercised: `ost 0.23.10`, on the same workstation as
  [report 03](03-2026-09-26-v0.23.8-report-02-reverified.md) (Windows 11,
  MSVC 14.51, NVIDIA RTX A5000); runtimes `cy2026-windows-x86_64-py313-lookdev`
  (OpenUSD 26.08, adopted from a local build) and `…-usd` (the canonical
  `26.08-gl-windows-x86_64` leaf)
- Occasion: composing the VRM `usdview` host session as a Formation — the
  runtime, `usd-vrm-plugins`' `vrmImaging` and this repository's renderer —
  as [renderer report 05](../renderer/05-2026-09-26-vrm-usdview-session.md)
  records; open-strata keeps this pairing as "downstream evidence not
  recorded" in its
  [combined Formations](https://github.com/animu-sphere/open-strata/blob/main/docs/projects/combined-formations.md#contract-status-versus-project-evidence)
- Prior report: [03](03-2026-09-26-v0.23.8-report-02-reverified.md)
- Next ask target: the next `ost` release

## TL;DR

**Every step up to `ost formation resolve` runs, and resolve refuses the
first component it checks. Four more gaps sit on the way there. Composed by
hand from the same packages, the session works, so what is missing is
`ost`'s.**

1. **P1, blocking:** `ost formation resolve` accepts a component only if its
   target starts with `<platform>-<os>-<arch>-<abi>-py<ver>`, and no package
   `ost` writes has that target (§2).
2. **P2:** `ost package` has no `--intent`, so a renderer whose Hydra
   adapter is built by an intent cannot package it (§3).
3. **P3:** the renderer component's contract puts `plugin/usd` on
   `PXR_PLUGINPATH_NAME`; the renderer template installs its plugin under
   `lib/usd/hd<Name>/resources` (§4).
4. **P4:** packaging a plugin for a second profile means re-pinning the
   workspace's only `strata.lock`, which `ost build` does by itself and
   `ost plugin build` does not (§5).
5. **P5:** there is no canonical runtime with `usdview` (§6).

## 1. What was done

```sh
ost runtime validate cy2026 --profile lookdev
ost runtime export cy2026 --profile lookdev --slim
ost runtime pull cy2026 --profile lookdev --from-artifact <digest> --force
ost build --profile lookdev --jobs auto
ost package --profile lookdev
ost artifact import <dist>
ost plugin build plugins/vrmImaging --profile lookdev      # in usd-vrm-plugins
ost plugin package plugins/vrmImaging --profile lookdev
ost formation resolve <formation>.toml
ost runtime explain cy2026 --profile lookdev
```

## 2. P1 — `formation resolve` refuses every packaged target

The Formation pinned the exported `lookdev` runtime, `vrmImaging` as a
`plugin` and `toon` as a `renderer`:

```text
$ ost formation resolve vrm-usdview.toml
error[FORMATION_INCOMPATIBLE_COMPONENT]: component 'vrmImaging' is incompatible: target 'cy2026-windows-x86_64-py313-lookdev' does not match runtime platform 'cy2026' and variant 'windows-x86_64-msvc143-py313'
  hint: select an artifact built and validated against the pinned runtime
```

The runtime and `toon` alone fail the same way on `toon`. So does a
Formation with nothing of ours in it: the canonical `usd` runtime and a
`vrmSchema` 0.9.0 package `ost plugin package` built against it
(`target 'cy2026-windows-x86_64-py313-usd'`).

`validate_target` in `crates/ost-formation/src/lib.rs` accepts a component
whose target equals the variant slug or starts with
`<platform>-<variant slug>`. The variant slug carries the ABI
(`windows-x86_64-msvc143-py313`); a package target does not
(`cy2026-windows-x86_64-py313-<profile>`). On Linux the slug carries
`glibc<ver>` and the target does not, so the check cannot pass there either.
It was not run on Linux.

**Ask (P1):** match a component's target by platform, OS, architecture,
Python and profile against the runtime's, and leave the ABI to the
compatibility checks that already read `compatibility.abi`. A test that
resolves a Formation from real `ost package` and `ost plugin package`
outputs would have caught this. Raised as [open-strata#251](https://github.com/animu-sphere/open-strata/issues/251).

## 3. P2 — `ost package` cannot package an intent

This repository's Hydra adapter is built by the `hydra` intent
(`TOON_ENABLE_HYDRA2`). `ost package` has no `--intent` and reads only
`build/<target>`, so after `ost build --profile lookdev --intent hydra` it
reports `target '…-lookdev' is not built`. The package here was made from an
intentless `lookdev` build with `TOON_ENABLE_HYDRA2=ON` set in its CMake
cache — which the next reconfigure dropped: re-pulling the runtime made
`ost build` configure afresh with the option off, and a package made then
would have carried no renderer.

**Ask (P2):** `ost package --intent <name>`, reading
`build/<target>--<intent>` and recording the intent in the manifest. Raised as [open-strata#252](https://github.com/animu-sphere/open-strata/issues/252).

## 4. P3 — the renderer contract names a directory the template does not install

`ost package` writes a `renderer` component whose environment prepends
`plugin/usd` to `PXR_PLUGINPATH_NAME`. The renderer template installs the
plugin to `lib/usd/hd<Name>/` with its `plugInfo.json` in `resources/`
(template README: `<stage>/lib/usd/hd{{Name}}/resources`), and the package's
own file list has no `plugin/` at all. In `testusdview` with the declared
directory, `--renderer Toon` is rejected (`choose from 'Storm', 'GL'`); with
`lib/usd/hdToon/resources` it draws (renderer report 05 §2).

**Ask (P3):** derive the component's plugin path from the installed
`plugInfo.json`, or install the template's plugin where the contract says. Raised as [open-strata#253](https://github.com/animu-sphere/open-strata/issues/253).

## 5. P4 — one lock per workspace, and two builders that treat it differently

`usd-vrm-plugins` pins the `usd` runtime. After `ost plugin build …
--profile lookdev` the pin is still `usd`, and `ost plugin package …
--profile lookdev` stops with `PACKAGE_RUNTIME_LOCK_MISMATCH` until
`ost lock --profile lookdev` re-pins it. The packages above were made that
way, and `ost lock` restored the `usd` pin, which `ost lock --check`
confirmed. Here, `ost build --profile lookdev` re-pins this repository's
`strata.lock` from `core` to `lookdev` by itself, so `ost package --profile
lookdev` found them matching; `ost lock` puts `core` back.

**Ask (P4):** one rule for `ost build` and `ost plugin build`, and a way to
package for a second profile that does not rewrite the pin a workspace's CI
reads. Raised as [open-strata#254](https://github.com/animu-sphere/open-strata/issues/254).

## 6. P5 — no canonical runtime has `usdview`

The canonical matrix (`support/openusd-runtime-matrix.json`) produces the
`usd` profile only. Its `26.08-gl-windows-x86_64` leaf has the imaging
libraries but not `usdview` or the `hydra-preview` capability, so a
`usdview` host session needs `lookdev`, and the `lookdev` here is a local
OpenUSD build adopted with `--from-usd`. It carries oneTBB 2021.12; a
managed `--build` for CY2026 would pin 2022.1.0. It validated, exported
with `--slim` and re-materialized with the same runtime digest. No source
identity was recorded for it.

`ost runtime explain cy2026 --profile lookdev` still describes OpenUSD
25.05.01 as certified, with a range of `>=25.05,<26.08`, while the runtime
it resolves to is 26.08 and validates.

**Ask (P5):** a canonical `lookdev` leaf with `usdview`, named as the `usd`
leaves are (`openstrata-runtime-cy2026-lookdev`,
`26.08-gl-<os>-<arch>`), for Windows and Linux at least; and an `explain`
that describes the version the catalogue now resolves. Raised as [open-strata#255](https://github.com/animu-sphere/open-strata/issues/255).
