# A Hydra-fed viewport through `ost renderer viewport`: the renderer template turns the intent's Hydra adapter off, the run reuses and rewrites the intent's build tree, and the launch cannot add a plugin

- Date: 2026-09-28
- Version exercised: `ost 0.23.13`, on the workstation of
  [report 06](06-2026-09-27-v0.23.13-report-05-reverified.md) (Windows 11,
  MSVC 14.51, NVIDIA RTX A5000); the canonical CY2026 `lookdev` runtime
  (OpenUSD 26.08). The source read is `open-strata` at `v0.23.13-7-ge4a5fd8`,
  where `crates/ost-cli/src/commands/renderer.rs` and
  `templates/renderer/CMakeLists.txt` are unchanged since `v0.23.13`
- Occasion: this repository's
  [design policy §31](../../design/DESIGN_POLICY.md#31-evaluation-hosts)
  makes `toon-viewport` the renderer's main evaluation host, fed a USD
  stage through Hydra in its own frame loop, as `hydra-merlin`'s
  `merlin-viewport` is fed one
  (`ost renderer viewport --intent viewport-usd --profile usd -- --usd <stage>`
  in its README). Before building that, this report measures what `ost`
  gives a template-generated renderer on the same path
- Prior report: [06](06-2026-09-27-v0.23.13-report-05-reverified.md)
- Next ask target: the next `ost` release

## TL;DR

**A renderer generated from the `renderer` template cannot build its Hydra
adapter and its viewport into one tree through `ost renderer viewport`, and
trying leaves the Hydra intent's own tree silently without its adapter.
`hydra-merlin` does not meet this because it was adopted, not generated: its
CMake never reads `OST_RENDERER_ADAPTERS`.** Three asks come out of it.

1. **Q1:** the viewport workflow sets `OST_RENDERER_ADAPTERS=viewport`, the
   template's CMake then forces `<NAME>_ENABLE_HYDRA2` from that list, so an
   intent's `TOON_ENABLE_HYDRA2=ON` ends `OFF`; an intent that asks for
   `hydra2;viewport` itself is refused as `INVALID_CONFIG` (§2).
2. **Q2:** `ost renderer viewport --intent hydra` builds in
   `<target>--hydra`, the tree `ost build --intent hydra` owns, and leaves
   `OST_RENDERER_ADAPTERS=viewport` in its cache. The next
   `ost build --intent hydra` keeps it, builds no Hydra adapter, and
   `ost test` and `ost validate --intent hydra` pass with every Hydra
   assertion `SKIP` (§3).
3. **Q3:** the viewport is launched in the runtime's environment and nothing
   else. There is no `--with`, as `ost plugin view` has, and no way to take
   a Formation's components, so a Hydra-fed viewport cannot have
   `vrmImaging` in its process, and a VRM avatar in it cannot select MToon
   (§4).

## 1. What was done

```sh
ost --version                                        # ost 0.23.13
ost renderer viewport --intent hydra --profile lookdev --preflight [--json]
ost renderer viewport --intent hydra --profile lookdev --preflight --json -- <arg>
    # <arg>: --usd x.usda | usdview-smoke.usda | --stage <path>/usdview-smoke.usda
ost renderer viewport --intent hydra --profile lookdev --json --redact-paths \
    -- --frames 8 --hidden
ost build --profile lookdev --intent hydra --jobs auto
ost test --profile lookdev --intent hydra
ost validate --profile lookdev --intent hydra
# a temporary intent in openstrata.toml, removed afterwards:
#   [build.intents.viewport-usd]
#   cache = { TOON_ENABLE_HYDRA2 = …true, OST_RENDERER_ADAPTERS = …"hydra2;viewport" }
ost renderer viewport --intent viewport-usd --profile lookdev --preflight
#   … and again with OST_RENDERER_ADAPTERS = "viewport"
```

`toon-viewport` does not read a USD stage yet: the runs measure what `ost`
builds and launches, not a Hydra-fed frame.

## 2. Q1 — the intent's Hydra adapter is turned off

`ost renderer viewport` resolves the declared intent and inserts
`OST_RENDERER_ADAPTERS=viewport` into its cache (`insert_domain_cache` in
`renderer.rs`). The preflight shows the combined cache:

```json
"intent": { "name": "hydra", "cache": {
  "OST_RENDERER_ADAPTERS": { "type": "STRING", "value": "viewport" },
  "TOON_ENABLE_HYDRA2":    { "type": "BOOL",   "value": "ON" } } }
```

The template's `CMakeLists.txt`, which this repository's is generated from,
treats a non-empty `OST_RENDERER_ADAPTERS` as the whole adapter set and
writes both options from it with `FORCE`:

```cmake
if(_{{NAME}}_MANAGED_ADAPTER_INTENT)
  set({{NAME}}_ENABLE_HYDRA2 ${_{{NAME}}_HYDRA2_DEFAULT} CACHE BOOL "…" FORCE)
  set({{NAME}}_ENABLE_VIEWPORT ${_{{NAME}}_VIEWPORT_DEFAULT} CACHE BOOL "…" FORCE)
```

The configured tree after the run:

```text
OST_RENDERER_ADAPTERS:STRING=viewport
TOON_ENABLE_HYDRA2:BOOL=OFF
TOON_ENABLE_VIEWPORT:BOOL=ON
```

Asking for both adapters in the intent is the next thing to try, and it is
refused before anything is configured, because the inserted value must equal
a declared one:

| Intent's `OST_RENDERER_ADAPTERS` | Preflight |
| --- | --- |
| not declared | passes; the tree ends with Hydra `OFF` |
| `"hydra2;viewport"` | `Error[INVALID_CONFIG]: build intent 'viewport-usd' sets OST_RENDERER_ADAPTERS incompatibly with this renderer workflow` |
| `"viewport"` | passes; Hydra `OFF`, as the first row |

So the template's two routes — `ost renderer view` asking for `hydra2`, and
`ost renderer viewport` asking for `viewport` — each get one adapter, and no
declared intent gets both. `hydra-merlin`'s `viewport-usd` intent sets
`MERLIN_ENABLE_HYDRA2` and `MERLIN_BUILD_VIEWPORT` directly, and its
`CMakeLists.txt` and `cmake/` have no `OST_RENDERER_ADAPTERS` in them, so the
inserted value changes nothing there.

**Ask:** let the viewport workflow *add* `viewport` to an intent's adapter
set — accept a declared list that contains it, or merge into it — and have
the template read the list as a request for adapters on top of the intent's
explicit options, not as the complete set. A template project could then
declare, as `hydra-merlin` does:

```toml
[build.intents.viewport-usd]
cache = { OST_RENDERER_ADAPTERS = { type = "STRING", value = "hydra2;viewport" } }
```

## 3. Q2 — the viewport run rewrites the intent's build tree, and nothing notices

With `--intent hydra`, the viewport run built in
`build/cy2026-windows-x86_64-py313-lookdev--hydra`, the directory
`ost build --profile lookdev --intent hydra` uses. The default viewport run,
without an intent, has a tree of its own (`…-core--renderer-viewport`).

The `hydra` intent does not declare `OST_RENDERER_ADAPTERS`, so an ordinary
build of it afterwards passes nothing for it, and the cached `viewport`
stays. Measured in order:

| Step | Cache after it | Result |
| --- | --- | --- |
| an earlier `ost build --profile lookdev --intent hydra` | Hydra `ON` | `hdToon.dll` in the tree |
| `ost renderer viewport --intent hydra --profile lookdev -- --frames 8 --hidden` | `viewport`, Hydra `OFF`, viewport `ON` | exit 0, 8 frames presented |
| `ost build --profile lookdev --intent hydra` | unchanged: Hydra `OFF` | exit 0 in 2.3 s |
| `ost test --profile lookdev --intent hydra` | — | **5 of 5 passed** |
| `ost validate --profile lookdev --intent hydra` | — | **`Result: passed`**, with `renderer.plugin.discovery`, `.delegate.creation`, `.render_buffer.cpu`, `.host.first_frame` and `.host.stable_update` each `SKIP` — "configure with TOON_ENABLE_HYDRA2=ON" |

The intent whose whole purpose is the Hydra adapter validates without it.
The stale `hdToon.dll` of the earlier build stays in the tree, but no test
reaches it.

Recovering needed a step `ost` does not offer: `ost build` has no option to
reconfigure from scratch, so the tree's `CMakeCache.txt` was deleted by hand,
after which `ost build --intent hydra` configured Hydra `ON` and
`OST_RENDERER_ADAPTERS` empty, `ost test` passed 10 of 10, and every Hydra
assertion was `ok` again.

**Ask:** give a viewport run with an intent a tree of its own
(`<target>--<intent>--renderer-viewport`, as the intent-less run already
has), or have an ordinary `ost build` reset `OST_RENDERER_ADAPTERS` when the
intent does not set it. Separately, `ost validate --intent <x>` passing while
the adapter `<x>` exists to build is `SKIP` looks worth a check: an intent
could name the adapters it requires, so that their assertions stop being
skippable in that intent.

## 4. Q3 — the viewport cannot be given a plugin

After building, `ost renderer viewport` starts the executable with
`command.envs(resolved.env.resolve())`: the selected runtime's activation
environment, which on Windows carries OpenUSD's DLL directories on `PATH`.
That is what a Hydra-fed viewport needs to start, and a stage argument is
recognized: any passthrough argument naming a `.usda` file — `--usd x.usda`,
a bare path, `--stage <path>` — made the preflight request and apply the
`usd-stage-read` capability.

What it cannot do is add anything to that environment. For comparison:

| Command | Local build | Adds a plugin to the session |
| --- | --- | --- |
| `ost plugin view --with <bundle>` | a plugin workspace | yes |
| `ost renderer view` | this renderer, in `usdview` | only its own `plugInfo.json` (`PXR_PLUGINPATH_NAME` prepend); no `--with` |
| `ost renderer viewport` | this renderer's viewport | nothing beyond the runtime |
| `ost formation run` | none: every component is a digest-pinned artifact | yes, the Formation's components |

`hdToon` selects MToon only when `vrmImaging` contributes its `vrm`
container to the stage scene index
([renderer report 06](../renderer/06-2026-09-27-vrm-formation.md)): 12 of 12
VRM materials with it, 0 without. A Hydra-fed `toon-viewport` in this
launch environment would draw a VRM avatar with every material as
PreviewSurface. The Formation route works — it is how the `usdview` session
runs today ([renderer report 13](../renderer/13-2026-09-28-host-session-formation.md)) —
but only for a published or locally imported `toon` package, so each change
to the viewport would be packaged and imported before it could be looked at.

**Ask:** `ost renderer viewport --with <plugin bundle | workspace product |
artifact digest>`, composed into the launch environment as
`ost plugin view --with` composes a session, and recorded in the launch
record; the same for `ost renderer view`. Taking the components of a
Formation, with the renderer replaced by the local build, would serve as
well.

## 5. Observations

- **The launch record's `device` is `null`**, `device_status: unreported`:
  `ost` reads `Selected backend:`, `Device:` and `Presentation:` from the
  viewport's output, and `toon-viewport` prints `Presenting on: <device>`.
  That is this repository's to change, not `ost`'s.
- The launch record now carries the child's `stdout` (`Presenting on: NVIDIA
  RTX A5000, 4 sample(s) per pixel`, `Presented 8 frames …`). Report 06's
  empty streams were Formation run evidence, which was not re-measured.
