# `ost` 0.23.13 resolves report 05: the VRM renderer Formation's own `testusdview` command runs, from any directory

- Date: 2026-09-27
- Version exercised: `ost 0.23.13`, on the same workstation as
  [report 05](05-2026-09-27-v0.23.11-report-04-reverified.md) (Windows 11,
  NVIDIA RTX A5000, host CPython 3.13 at the user's default install); the
  runtime, `vrmImaging` and `toon` artifacts of report 05, unchanged
- Occasion: re-verifying report 05's two asks against the release that
  answers them ([v0.23.13 release notes](https://github.com/animu-sphere/open-strata/blob/main/docs/releases/v0.23.13.md);
  its [verification report](https://github.com/animu-sphere/open-strata/blob/main/docs/reports/2026-09-27-v0.23.13-formation-launch.md))
- Prior report: [05](05-2026-09-27-v0.23.11-report-04-reverified.md)
- Next ask target: the next `ost` release

## TL;DR

**Both of report 05's asks are answered. `ost formation run` starts the
Formation's declared `testusdview` command as written, with no interpreter
path and no launcher, and it does so from a manifest directory deeper than
the one that broke Qt in report 05. Every row of
[renderer report 06](../renderer/06-2026-09-27-vrm-formation.md)'s material
table reproduces.** Two of report 05's observations still hold, and no new
ask comes out of this run.

1. **Q1 answered:** `run` selects the host interpreter the runtime was
   validated with, puts its directory on the composed `PATH`, and launches
   the extensionless `testusdview` script through it (§2).
2. **Q2 answered:** the materialization root is
   `$OST_HOME/artifacts/f/<16-character id>/`, whatever the manifest's
   directory, and a run's transient tree is removed when it ends (§3).
3. **Still observed:** the run evidence's `stdout` and `stderr` are empty,
   and `toon`'s `lib` and `bin` are each on `PATH` twice (§4).

The declared command is renderer report 06's:

```toml
[command]
program = "testusdview"
args = ["material-probe.usda", "--renderer", "Toon", "--testScript", "vrm_material_check.py"]
```

Its arguments are relative to the working directory `run` is called from,
so the first run, from the probe's own directory, stopped at
`Invalid file supplied, does not exist: vrm_material_check.py` — already
inside `testusdview`, past the point where report 05's run failed. Every run
after it was made from one directory holding both files. The avatar runs
override only the stage: the program is still the bare `testusdview`.

## 2. Q1 — the declared command starts

| Formation | Stage | Exit | Renderer | `materials_preview` | `materials_mtoon` |
| --- | --- | --- | --- | --- | --- |
| runtime + `vrmImaging` + `toon` | `material-probe.usda` | 0 | `HdToonRendererPlugin` | 1 | 1 |
| runtime + `toon` | `material-probe.usda` | 0 | `HdToonRendererPlugin` | 2 | 0 |
| runtime + `vrmImaging` + `toon` | converted avatar | 0 | `HdToonRendererPlugin` | 1 | 12 |
| runtime + `toon` | converted avatar | 0 | `HdToonRendererPlugin` | 13 | 0 |

These are renderer report 06's counts, exactly, now from the Formation's own
command instead of a host `python.exe` and a `runpy` launcher. The avatar
uploaded its 20 meshes' topology and points once each, as before.

The run record names what `run` chose, which report 05 had to reconstruct by
hand:

```text
program    = testusdview
script     = C:/Users/…/.ost/artifacts/f/53f02c5d47b1ac16/runtime/bin\testusdview
python     = C:\Users\…\AppData\Local\Programs\Python\Python313\python.exe
executable = C:\Users\…\AppData\Local\Programs\Python\Python313\python.exe
```

The last entry `formation env` prepends to `PATH` is the interpreter's
directory, so it comes first. `formation.lock` did not change and names no
interpreter: the interpreter is recorded in the run, not the lock, so the
lock stays portable. `doctor` still
reports `'testusdview' is reachable`, and now that is what `run` does. The
wrong-ABI and missing-interpreter diagnostics the release notes describe
were not exercised here.

## 3. Q2 — the materialization root no longer follows the manifest

Report 05's run failed from a 104-character manifest directory, with
`qwindows.dll` at 254 characters. Here the same Formation, copied into a
154-character directory, ran the declared command to exit 0 with the same
counts as the first row above. The tree it ran from was
`C:/Users/…/.ost/artifacts/f/<16-character id>/`, which puts the runtime's
Qt platform plugins at the same depth whatever directory the manifest is in.

After each `run`, `artifacts/f/` held no tree. `formation env` left its tree
in place, as the release notes describe for `env`, and the next `env` or
`run` does not reuse it.

## 4. Observations

- **Run evidence still has empty `stdout` and `stderr`** for a command that
  printed its renderer and frame to the console (report 05 §5). The record
  is otherwise complete, and it now carries `script` and `python`.
- **`toon`'s directories are on `PATH` twice**: `components/toon/lib` twice
  and `components/toon/bin` twice in `formation env`. Report 05 saw `lib`
  twice; `bin` is doubled too. Harmless.
- **A plugin carried by a component and listed beside it** (report 05 §5)
  was not re-measured: neither Formation here lists `vrmSchema` on its own.
