## TL;DR

**Stage 3 is in. The WebGPU backend draws the shared shadow views, one
to four, with the shared caster pass into a depth32float array before the
scene, and MToon, PreviewSurface and MMD receivers read them, MMD's
self-shadow among them. `toon-viewport --backend webgpu` presents through
the window's surface: the scene into a reusable linear foreground, the
composite into an sRGB view, captures, the foreground PNG, the host's
overlay with its shadow-view previews, live sample changes and GPU pass
timing. Six new parity scenes with shadows are identical to Vulkan at 1x
through either of Dawn's adapters, and within one step at 4x, but for two
Mask pixels whose shares sit on a coverage threshold, one of them keeping
sample 0 on one backend only; that WGPU-Q1 class now allows sample 0's
coverage to differ where it does. The
viewport's presented image is byte-identical to the Vulkan session's at
1x and 4x. The headless run's five shadow checks pass on WebGPU, 31 checks
in all. Core WebGPU timestamps only whole passes, so the session times
the scene pass whole and says its parts are unmeasured, and Dawn's
timestamp quantization, which rounds to 2^16 ns, is turned off for it.
Vulkan's images and SPIR-V are unchanged.**

## 1. Shadows

The core's `ShadowFit` already fits backend-neutral views (shadow policy
§5), so the backend's part is the image, the caster pass and the
receivers' parameters, as the Vulkan backend's `ShadowMap`:

- **Image.** A depth32float two-dimensional array, a layer per view, built
  at the default resolution with one layer and rebuilt when the resolution
  changes or a frame draws more views than it has layers. The frame group
  binds it with every view's parameters and MMD's, so a rebuild makes the
  frame group again (`MaterialCache::BindFrame`).
- **Writers.** The views' and MMD's parameter records are filled the same
  way on both backends, so `WriteShadowParameters` joins the shared
  writers in `backend/shared/`. The Vulkan backend calls it too: the 88
  Vulkan images of the parity run below, its 22 scenes at 1x and 4x over
  both clears, are byte-identical before and after.
- **Caster pass.** A pass per view, before the scene, with the shadow
  pipeline's state as on Vulkan: points and UVs, depth alone at one sample,
  bias 1 and slope 1, faces by the caster's role, Mask casters cut by
  their slot's alpha. A pass that draws into a layer cannot bind the
  array, which WebGPU counts as the same resource in one usage scope, so
  the caster pipeline's group 0 is the frame buffer alone, for a cut's UV
  animation time. A view's clip space keeps y up, and the receivers read
  its rows with row 0 at y = -1, which a WebGPU target puts at the
  bottom; the casters draw with y flipped
  (`WebGpuShadowClipFromWorld`), so each layer holds the Vulkan backend's
  rows, and a face counter-clockwise in the scene is clockwise in the
  view, as on Vulkan.
- **Ring.** The casters' draw constants go first in the frame's ring, the
  scene's after them; the ring's bound is three draws per part and one per
  part and view.

The shadow WGSL (`scene/shadow.slang`) passes Tint unchanged. The
receivers' WGSL was already there: stage 2 bound a 1 x 1 placeholder and
named no view.

## 2. Shadow parity

`toon-webgpu-parity` gains six scenes, drawn with shared shadows and MMD's
self-shadow on, as a frame is by default; stage 1 and 2's sixteen keep
both off, so their numbers stand. Each run also requires both backends to
draw the same number of views, caster draws and MMD caster draws.

- **shadow-mtoon**: an MToon sphere over an MToon ground under a
  directional key.
- **shadow-preview-spot**: two PreviewSurface spheres, one metallic, over a
  PreviewSurface ground, under a directional light and a spot: two views.
- **shadow-mmd-self**: MMD's self-shadow under the fallback key, a sphere
  and a double-sided floor that both cast and receive.
- **shadow-cross-family**: an MToon caster, an MMD caster and a
  display-colour caster over MMD, PreviewSurface and MToon tiles.
- **shadow-mask-caster**: an MToon Mask plane cut by its base texels'
  alpha and a PreviewSurface Mask plane cut by its opacity, over an MToon
  ground.
- **shadow-four-views-skinned**: two directional lights and two spots, four
  views, over a skinned and morphed MToon caster.

Largest channel difference, pixels more than one step apart (of 16,384)
and largest depth difference, the worse of the two clears; views and
caster draws are equal on both backends in every row:

| Scene | Views, casters | 1x, Direct3D 12 | 4x, Direct3D 12 | 1x and 4x, Dawn's Vulkan adapter |
| --- | --- | --- | --- | --- |
| shadow-mtoon | 1, 2 | 0, 0, 1.2e-7 | 0, 0, 1.2e-7 | 0, 0 |
| shadow-preview-spot | 2, 6 | 0, 0 | 1, 0 | 0, 0 |
| shadow-mmd-self | 1, 2 | 0, 0 | 0, 0 | 0, 0 |
| shadow-cross-family | 1, 5 | 0, 0 | 0, 0 | 0, 0 |
| shadow-mask-caster | 1, 3 | 0, 0 | 64, 2 | 0, 0 at 1x; 64, 2 at 4x |
| shadow-four-views-skinned | 4, 8 | 0, 0, 1.8e-7 | 0, 0, 1.8e-7 | 0, 0 |

The shadows themselves are identical: every difference above one step is
the Mask plane's, and turning shadows off leaves the same pixels.

**The Mask row.** Its two pixels lie on the MToon Mask plane's alpha edge,
stage 2's class of a share on a coverage threshold keeping one sample
more. One of them, (27, 45), also differs in the depth product's coverage,
which that class had required to be identical. The ground's far edge
crosses that pixel at y = 45.61, so samples 2 and 3 lie on the ground and
0 and 1 beyond it. Vulkan keeps one sample of the plane, sample 3, and
WebGPU two, samples 3 and 0: two covered samples without sample 0 against
three with it. The kept samples nest in the order 3, 0, 1, 2 (report 92),
so whenever a threshold share falls between one sample and two, the extra
sample is sample 0, which the depth product resolves. Two checks back this
reading:

- The coverage probe, widened from one 2 x 2 dither block to 8 x 8, keeps
  the same count and sample 0 alike on every pixel for all 256 shares,
  12,288 partial readings; the dither's period is 2 x 2.
- Sweeping 1,025 shares finds the only disagreements at the shares 7.47,
  55.6 and 119.5 in 255ths, within 0.2 of a threshold, each a count
  differing by one; none changes sample 0 alone.

The Mask class (`kMaskCoverageLimits`) now lets sample 0's coverage differ
on at most 2e-4 of its pixels, the share it already allows a sample more
on; the scene's 4x run uses it.

## 3. Headless checks

`toon-headless --backend webgpu` now runs the five shadow checks stage 2
skipped: MMD's self-shadow, shared casters, receivers, views (resolution,
bias, four views and one counted, the debug views) and the 192
cross-family cases. All pass through both of Dawn's adapters, 31 checks
in all, as the Vulkan run's 31. The bootstrap frame's persistence check
counted one pipeline; the bootstrap draw casts into the fallback key's
view, so it now requires the scene pipeline and the caster's, one view and
one caster draw.

## 4. Presentation

`CreateWebGpuPresentSession` (`include/toon/webgpu_present.hpp`) takes the
window as an HWND and its module, which the viewport reads through GLFW's
native header, and owns the surface, as the Vulkan session owns its
`VkSurfaceKHR`. The adapter is requested compatible with it.

- **Surface.** Dawn's Direct3D 12 adapter offers the window `BGRA8Unorm`,
  `RGBA8Unorm`, `RGBA16Float` and `RGB10A2Unorm`, no sRGB format, so the
  surface is configured as `BGRA8Unorm` with `BGRA8UnormSrgb` as a view
  format; its Vulkan adapter offers `BGRA8UnormSrgb` itself, which is
  taken directly. The composite and overlay write through the sRGB view,
  encoding the linear foreground once as the Vulkan session's sRGB
  swapchain does. Captures copy the texture's stored bytes, BGRA swapped
  to RGBA. Both adapters offer FIFO, immediate and mailbox: FIFO under
  vsync, immediate otherwise.
- **Frame.** The scene draws into a reusable linear premultiplied RGBA8
  foreground through the offscreen renderer's caches, shadow views
  included, resolving as the pass ends at 4x; then the composite, the
  foreground and presented copies a capture asks for, and an overlay pass
  that loads the presented image, so a capture never shows the overlay.
  One frame in flight: each frame waits for the previous submission's
  completion future before the late latch and before anything it read is
  touched. A sample change waits for it, makes the pipelines again as
  draws need them and the sample targets at the new count; no cache or
  bind group changes, and nothing is uploaded.
- **Overlay.** The viewport hands the backend Dear ImGui's draw data as an
  `OverlayDrawList`, and the Vulkan backend draws it with its own pass; so
  does this one, from the same `present/overlay.slang`. Policy §8 had said
  the overlay would use Dear ImGui's WebGPU backend; it is corrected. A
  shadow view's preview binds a depth32float layer, which WGSL reads only
  as an unfilterable float through a non-filtering sampler, so the overlay
  has a second bind group layout and pipeline for it.
- **Shaders.** `present/composite.slang` and `present/overlay.slang` take
  their WebGPU bindings under `TOON_WEBGPU`, a uniform in place of push
  constants and a texture and sampler in place of a combined image; their
  four Vulkan stages compile to the same SPIR-V as on `main`, byte for
  byte.

The presented image of one view, overlay off, the bootstrap scene with its
shadow, is byte-identical between the Vulkan and WebGPU sessions at 1x and
4x (`toon-viewport-webgpu-parity-1` and `-4`), through Dawn's Vulkan
adapter as well, and Dawn reported no validation error in any run.

## 5. Timing

Core WebGPU writes timestamps only as a pass begins and ends, and neither
of Dawn's adapters here offers its experimental timestamps inside passes
with the default toggles. So the WebGPU session times what lies between
passes' timestamps: uploads (the mip passes), the shadow views, the scene
pass whole, the composite, the capture copies between the composite and
the overlay, and the overlay. The scene's parts and the image wait are not
measured: `PresentStatistics::gpu_parts_timed` says so, the new
`PresentGpuTimes::scene` holds the pass (the Vulkan session fills it too,
from the image's release to the resolve), and the viewport's telemetry
leaves the parts' rows empty, which its overlay shows as `--`. The JSON
names `wgpuSurfacePresent_return` as the present endpoint.

Dawn rounds timestamps to 2^16 ns by default, a browser's guard against
timing attacks. The first runs read every pass as 0 or 0.066 ms; with the
`timestamp_quantization` toggle disabled for a device that asks for
timestamps, the same frames read a shadow pass of 0.015 ms and a scene pass
of 0.036 ms. The policy allows a toggle a report measures a reason for; a
native renderer timing its own passes is that.

The bootstrap scene, a lit triangle casting into the fallback key's view,
1,000 frames hidden at 4x without vsync, p50 and p99 in milliseconds, on
each backend's session. It is a sanity check of the timing path, not a
performance comparison, which stage 4 makes on the avatar and
`shadow-cost` fixtures:

| Part | Vulkan p50 / p99 | WebGPU p50 / p99 |
| --- | --- | --- |
| GPU shadow | 0.019 / 0.021 | 0.012 / 0.013 |
| GPU scene (Vulkan: unlit 0.007, opaque 0.022, resolve 0.011) | 0.041 / 0.046 | 0.026 / 0.027 |
| GPU composite | 0.009 / 0.010 | 0.010 / 0.012 |
| GPU overlay | 0.014 / 0.018 | 0.005 / 0.006 |
| GPU frame | 0.084 / 0.096 | 0.074 / 0.077 |
| CPU wait | 0.030 / 0.068 | 0.028 / 1.086 |
| CPU submit | 0.567 / 1.106 | 0.220 / 0.530 |
| frame interval | 0.651 / 1.221 | 0.301 / 1.375 |

WebGPU's CPU wait has a longer tail: under immediate presentation Dawn's
surface texture is sometimes not free when the frame asks for it, and the
wait for it is counted with the wait for the frame in flight.
